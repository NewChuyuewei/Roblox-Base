# Carbon 组件分册

> 总图是 `.plan/CARBON.md`；本文件把总图 §2 的每个组件展开成**功能块**，回答「这几千行具体是什么」。
> 层次、依赖、核心行数以 `scripts/carbon-manifest.luau` 为准；本文件每张表的行数之和等于清单里的 `core`（生成时核对过）。
>
> **效力**：功能块的划分与每块的行数是**提议**，没有任何一块经过纵切验证。
> 它的用处是让「铺得太薄」（总图 §8）在动工前就能看出来，而不是承诺。每个组件立项纵切后回写本文件。
> 文中的模块名是工作名，立项时可以改；组件名不可改（总图 §2）。
> 名为 `Host` 的功能块是该组件唯一可以碰引擎的部分（总图 §3.2）；没有列出 `Host` 的组件，若需要宿主能力，其行数从相邻功能块里出，立项时写明。

## 怎么读

| 栏 | 含义 |
| --- | --- |
| 定位 / 不做 | 这个组件负责什么，以及明确不归它的东西（防止两个组件各做一份，I21） |
| 功能块 | 核心代码的划分；行数单位是千行，不含 `Integration/` 与测试 |
| 第一刀 | 立项时的纵切：最小的、能在 Lune 里断言的端到端演示 |
| 先决 | 动工前必须先有的决策、实测或别的组件 |
| 深度 | 「完整」＝预算够做到功能完整；「最小可用」＝预算只够主路径，立项时要明确砍掉什么 |

顺序是按层排的；实际的先后与分批见 `.plan/PHASES.md`。

## 19. `Boron` — 反作弊引擎

L3 分布式与对抗 · 核心 5.5k 行 · 深度：最小可用

**形态（用户 2026-11-14）：参照 Minecraft 的 Vulcan 反作弊——做记录、拉回、踢出，不做封禁。**
（对 Vulcan 的描述来自我对它的一般了解：按检查项累计违规值，达到阈值后告警、拉回或执行处置；本环境无法联网核对其细节，这里只取这个工作方式，不照搬它的检查清单。）

- **定位**：服务端的检查框架。每个检查项独立判定、独立累计违规值，按阈值阶梯处置：**记录 → 告警 → 拉回 → 踢出**。
- **不做**：
  - **不做封禁**：没有封禁接口，也不保存封禁名单。记录可以被别的系统读走去做决定，那不在 `Boron` 内。
  - 不做客户端完整性检测（客户端不可信，检测代码本身可被绕过）。
  - 不做服务端重放与统计异常检测（原方案里有，5k 预算放不下，见下方「砍掉的」）。

**工作方式**

| 概念 | 含义 |
| --- | --- |
| 检查项 | 一个独立的判定，如「水平速度」「命中距离」。有名字、类别、开关和自己的配置 |
| 违规值 | 每个玩家在每个检查项上的累计值；每次判定失败增加，随时间衰减，合法行为不会越积越高 |
| 缓冲 | 判定失败先扣缓冲，缓冲用尽才增加违规值；用来吸收偶发的网络抖动 |
| 处置阶梯 | 每个检查项可配三个阈值：到告警阈值通知在线管理员；到拉回阈值把玩家放回上一个安全位置（或取消这次行为）；到踢出阈值断开连接 |
| 豁免 | 传送、被击退、乘坐载具、刚出生、服务端卡顿等期间，相关检查暂停或放宽 |
| 记录 | 每次违规一条：谁、哪个检查项、违规值、关键数值、延迟、位置、时间；可查询、可导出 |

| 功能块 | 内容 | 千行 |
| --- | --- | --- |
| Check | 检查项框架：注册、类别、开关、每项配置、违规值、缓冲与衰减 | 0.8 |
| Track | 每玩家状态：位置与速度历史、安全位置、延迟估计、豁免窗口 | 0.7 |
| Movement | 移动类检查：水平速度、飞行/悬空、跳跃高度、穿墙、瞬移、移动节奏（用 `Titanium` 做碰撞查询；带容差，不做逐位比对） | 1.2 |
| Combat | 战斗类检查：命中距离、命中朝向与遮挡、攻击频率 | 0.8 |
| Packet | 请求类检查：频率、顺序、非法参数、不可能的状态 | 0.4 |
| Punish | 处置阶梯：告警、拉回、取消行为、踢出；每项可单独关闭任一级 | 0.4 |
| Record | 违规记录、查询、留存期限、导出（经 `Phosphorus`） | 0.4 |
| Host | 拉回与踢出的引擎实现、位置采样、管理员告警的显示 | 0.8 |
| **合计** | | **5.5** |

- **第一刀**：只有「水平速度」一个检查项。喂入三段轨迹：超速的被记录、违规值越过阈值后被拉回到安全位置、继续超速则被踢出；一段有延迟抖动但合法的轨迹全程不触发。全程在 Lune 里用替身宿主断言，替身记录下「拉回到哪里」「是否踢出」。
- **先决**：
  - 误报率是验收指标：每个检查项立项时先定容差与阈值的默认值，并给出一组「合法但极端」的轨迹作为回归用例。
  - 清单里 `Boron` 的依赖是 `Titanium` · `Phosphorus`，端口 `Cesium`。管理员命令（开关告警、查记录）要用 `Neon` 的命令系统，需要**在清单里加上对 `Neon` 的依赖**（更低层，合法）；立项时改。
  - 没有 `Cesium` 也要能用：位置从 `Host/` 直接采样；接上 `Cesium` 后改用它的输入与快照，战斗类检查才能做延迟回溯。
  - Roblox 上角色移动默认由客户端模拟，所以拉回是服务端改写角色位置。这是我对平台的一般了解，立项时要实测拉回在各种网络条件下的表现。
- **砍掉的 / 放不下的**：服务端重放比对、统计异常检测（如点击间隔分布）、按检查项的自动调参。5.5k 行大约能做 13–16 个检查项；要更多检查项或加回上述两块，需要从别的组件挪预算，第一刀之后按实际行数再定（2026-11-15 上浮已先给 0.5k，其余仍挂 P15）。
