# Roblox 企业级数据库系统 — 开发指南

> 目标：在 DataStoreService 之上构建一个具备关系型严谨性、NoSQL 灵活性、B+ 树索引与企业级扩展能力的数据库引擎。代号建议：**VoxDB**（配合 Vospek 品牌）

---

## 一、核心设计哲学

DataStoreService 本质是一个 **KV 存储**（Key-Value），你要在它之上模拟出：

```
应用层
  └─ 查询语言层 (VQL — Vospek Query Language)
       └─ 查询规划器 / 优化器
            └─ 执行引擎
                 └─ 存储引擎 (B+树索引 + 页管理)
                      └─ DataStoreService (物理存储)
```

所有上层的"关系型"概念都是**逻辑抽象**，物理层永远只有 DataStore 的 KV。

---

## 二、存储层设计（Storage Engine）

### 2.1 命名空间规范

DataStore 的 key 是你唯一可控的结构维度，必须系统化设计：

```
[db]:[table]:[partition]:[key_type]:[value]

示例：
  vdb:users:p0:row:u_10023          → 行数据
  vdb:users:p0:idx:email:a@b.com    → 索引条目
  vdb:users:meta:schema             → 表结构定义
  vdb:__catalog__:tables            → 全局表目录
  vdb:__txn__:lock:u_10023          → 行级锁
  vdb:__seq__:users:id              → 自增序列
```

### 2.2 页（Page）抽象

不要直接存行数据，引入**页**的概念聚合小记录，减少 DataStore 调用次数：

```
Page 结构（存为一个 DataStore value）：
  {
    pageId: string,
    tableId: string,
    partition: number,
    slots: [            ← 槽位数组，类似 PostgreSQL heap page
      { slotId, rowId, data, deleted, txnId }
    ],
    freeSpace: number,
    nextPageId: string | null,
    lsn: number         ← Log Sequence Number，用于 WAL
  }
```

每页建议容量：**4KB 等效数据**（DataStore 单值上限 4MB，但要留余量给序列化开销）

### 2.3 分区策略

| 策略 | 适用场景 |
|---|---|
| Hash 分区 | 主键均匀分布，点查询为主 |
| Range 分区 | 时间序列、数值范围查询 |
| List 分区 | 枚举类型（如 region, gamemode） |

分区元数据存入 `__catalog__`，查询时由路由层决定访问哪个分区。

## 三、索引层设计（B+ 树）

### 3.1 B+ 树在 KV 上的映射

B+ 树每个节点 = 一个 DataStore key，节点结构：

```
内部节点：
  {
    nodeId, isLeaf: false,
    keys: [k1, k2, k3],          ← 分隔键
    children: [n1, n2, n3, n4]   ← 子节点 ID
  }

叶子节点：
  {
    nodeId, isLeaf: true,
    entries: [
      { key, rowId, pageId, slotId }  ← 指向实际行
    ],
    prevLeaf, nextLeaf               ← 双向链表，支持范围扫描
  }
```

根节点 ID 存入表元数据，树高建议控制在 **3~4 层**（受 DataStore 请求限制约束）。

### 3.2 索引类型

```
PRIMARY INDEX   → 聚簇，行数据随主键排序存储
SECONDARY INDEX → 非聚簇，叶节点存 (secondary_key → primary_key) 映射
UNIQUE INDEX    → 插入前验证唯一性（需要锁）
COMPOSITE INDEX → 多列联合键，按列优先级排序
PARTIAL INDEX   → 带 WHERE 条件的稀疏索引（过滤后建立）
```

### 3.3 索引维护

- **写入路径**：行插入 → 找目标叶节点 → 插入 entry → 若节点满则分裂（split）→ 向上传播
- **删除路径**：标记删除（软删除）→ 异步合并（merge）低于半满的兄弟节点
- **VACUUM 机制**：定期清理软删除条目，重构过于稀疏的页

## 四、关系型模型层

### 4.1 Schema 系统

```
Table Schema（存入 meta:schema）：
  {
    tableId, tableName, version,
    columns: [
      { name, type, nullable, default, primaryKey, unique }
    ],
    constraints: [
      { type: "FK", column, refTable, refColumn, onDelete }
      { type: "CHECK", expr }
    ],
    indexes: [ { indexId, columns, type, unique } ]
  }
```

Schema 版本号用于**在线 Schema 变更**（Online DDL），不锁表，旧行按需迁移。

### 4.2 数据类型系统

| VoxDB 类型 | 内部表示 | 说明 |
|---|---|---|
| `INT`, `BIGINT` | number | Lua number 精度边界需注意 |
| `FLOAT` | number | |
| `VARCHAR(n)` | string + 截断验证 | |
| `TEXT` | string | 超长时分块存储 |
| `BOOLEAN` | boolean | |
| `TIMESTAMP` | number (Unix ms) | |
| `UUID` | string | 生成策略见下 |
| `JSON` | table（嵌套） | NoSQL 灵活性入口 |
| `ARRAY<T>` | table（数组） | |
| `ENUM` | string + 校验集合 | |

### 4.3 外键与完整性约束

外键不依赖数据库原生支持，在**执行引擎层**强制检查：
- INSERT/UPDATE 时验证引用行存在
- DELETE 时根据 `ON DELETE` 策略（CASCADE / SET NULL / RESTRICT）处理
- 约束检查失败 → 事务回滚

## 五、事务与并发控制（ACID）

### 5.1 事务模型

```
事务生命周期：
  BEGIN → [读/写操作] → COMMIT / ROLLBACK

每个事务持有：
  txnId (唯一), startTimestamp, status,
  readSet: [rowId],    ← 读过的行
  writeSet: [rowId],   ← 修改过的行（待提交）
  undoLog: [操作记录]  ← 回滚用
```

### 5.2 隔离级别实现

| 隔离级别 | 实现机制 |
|---|---|
| Read Uncommitted | 直接读，无保护 |
| Read Committed | 读时检查行锁 |
| Repeatable Read | MVCC 快照读 |
| Serializable | 两阶段锁（2PL）|

**推荐默认：Read Committed**（在 Roblox 请求限制下性能最优）

### 5.3 MVCC（多版本并发控制）

每行存储多版本：
```
Row:
  { rowId, data, createdTxnId, expiredTxnId }
```
- 读操作看到 `createdTxnId ≤ 当前txn` 且 `expiredTxnId = null 或 > 当前txn` 的版本
- 写操作创建新版本，旧版本设置 `expiredTxnId`
- 旧版本由 **VACUUM** 异步清理

### 5.4 锁管理器

```
锁粒度（从粗到细）：
  Table Lock → Partition Lock → Page Lock → Row Lock

锁类型：
  S (Shared)    → 读锁，多个事务可共持
  X (Exclusive) → 写锁，互斥
  IS / IX       → 意向锁，用于表/分区级别

死锁检测：
  维护等待图（Wait-For Graph），定期检测环路 → 选择代价最小的事务回滚
```

锁状态存入 `__txn__:lock:*`，DataStore UpdateAsync 的原子性保证锁操作原子执行。

## 六、WAL（预写日志）

Write-Ahead Log 是崩溃恢复的基础：

```
WAL 条目：
  { lsn, txnId, type, tableId, rowId, before, after, timestamp }

type: INSERT | UPDATE | DELETE | COMMIT | ROLLBACK | CHECKPOINT
```

- 所有数据变更先写 WAL，再写页
- WAL 存入专用 `OrderedDataStore`（利用其有序特性按 LSN 顺序存储）
- **Checkpoint**：定期将内存状态持久化，截断旧 WAL
- **Crash Recovery**：重启时 Redo 已提交事务，Undo 未提交事务

## 七、查询引擎

### 7.1 VQL 语法设计（参考 SQL）

```sql
-- 与 SQL 保持相似，降低学习成本
SELECT u.name, o.total
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE u.region = 'Asia' AND o.total > 100
ORDER BY o.total DESC
LIMIT 20;

-- NoSQL 风格 JSON 查询扩展
SELECT * FROM events
WHERE payload->>'type' = 'kill'
  AND payload->'meta'->>'weapon' = 'rifle';
```

### 7.2 查询规划器

```
SQL文本
  → Lexer / Parser → AST（抽象语法树）
  → Semantic Analyzer（验证表名、列名、类型）
  → Logical Plan（关系代数表达式）
  → Query Optimizer（代价估算，选择最优执行路径）
  → Physical Plan（具体算子树）
  → Executor（执行，返回结果集）
```

### 7.3 优化器策略

| 优化手段 | 说明 |
|---|---|
| 谓词下推 | WHERE 条件尽早过滤，减少中间结果集 |
| 索引选择 | 统计信息（基数、选择率）驱动索引决策 |
| Join 重排 | 小表驱动大表，减少嵌套循环代价 |
| 投影消除 | 只读取需要的列 |
| 常量折叠 | 编译期计算常量表达式 |

### 7.4 执行算子

```
基础算子：
  SeqScan     → 全页顺序扫描
  IndexScan   → B+树索引扫描
  IndexRangeScan → 范围扫描（利用叶链表）
  Filter      → 谓词过滤
  Project     → 列投影
  Sort        → 外部排序（分块归并）
  Limit/Offset

连接算子：
  NestedLoopJoin   → 通用，小数据集
  HashJoin         → 等值连接，大数据集
  MergeJoin        → 两端已排序时使用

聚合算子：
  HashAggregate    → GROUP BY 实现
  StreamAggregate  → 有序输入时
```

## 八、NoSQL 扩展层

### 8.1 文档模式

表中的 `JSON` 类型列支持嵌套文档，可对 JSON 路径建立**函数索引**：

```
CREATE INDEX idx_weapon ON events ((payload->>'weapon'));
```

### 8.2 时序模式

专用时序表，主键为 `(entity_id, timestamp)`，按时间分区：
- 自动 Downsampling（降采样）旧数据
- 滑动窗口聚合查询
- 适合：玩家行为日志、游戏内统计

### 8.3 图模式

边表设计：`(src_id, edge_type, dst_id, properties)`
- 双向索引支持出边 / 入边查询
- 适合：玩家关系图、任务依赖图

## 九、企业级特性

### 9.1 连接池 / 请求队列

DataStoreService 有严格的请求限速，必须设计请求队列：

```
架构：
  上层操作 → RequestQueue（按优先级排序）
           → RateLimiter（令牌桶算法）
           → BatchExecutor（合并可批量操作）
           → DataStoreService

优先级：
  P0 - 事务提交 / 崩溃恢复
  P1 - 玩家数据读写
  P2 - 索引维护
  P3 - VACUUM / 统计收集
```

### 9.2 缓存层

```
L1 Cache（进程内，ModuleScript 持有）：
  - 行缓存（LRU，按页为单位）
  - 索引节点缓存（热点 B+树节点常驻）
  - Schema 缓存

L2 Cache（Memory Store，跨服务器）：
  - 热点行跨服共享
  - 分布式锁辅助

缓存一致性：
  Write-Through（写时同时更新缓存和存储）
  或 Write-Behind（延迟写，依赖 WAL 保证不丢失）
```

### 9.3 统计信息收集器

优化器依赖统计信息做决策，需异步收集：
```
每表维护：
  行数估算, 列基数（Cardinality）, 
  直方图（值分布）, 最小/最大值,
  索引高度, 页数
```

### 9.4 在线 DDL（不停服 Schema 变更）

```
流程：
  1. 新 Schema 写入，version+1
  2. 后台进程渐进式迁移行（每次迁移 N 行）
  3. 读取时检查行版本，按需实时迁移（Lazy Migration）
  4. 所有行迁移完成后，切换 active schema version
  5. 清理旧版本元数据
```

## 关键设计约束提示

- **DataStore 请求限速**是整个系统的物理天花板，所有设计都要围绕**减少请求次数**展开（页聚合、缓存、批处理）
- **Lua 无多线程**，并发靠 `task.spawn` 协程模拟，锁实现需格外小心避免协程饥饿
- **MemoryStoreService** 是你的 L2 缓存和分布式锁的天然载体，合理利用
- B+ 树层高每增加一层，最坏情况多一次 DataStore 读，树高控制是性能关键

这套架构可以作为 Xe Essential 框架的数据层，也可以独立发布为 Vospek 的开源基础设施项目。
