# headless 能力基线（Step 7 探针结果）

> 探针：`scripts/probe-headless.luau`（可重跑；25 项，2026-10-25 实测于 Lune 0.11.1）。
> 本文件是**工具链与架构决策的依据**，不是介绍。门禁 2（"headless 测试在 CI 跑"）的落地方式由它决定。

---

## 1. 结论摘要（先看这个）

| 问题 | 结论 |
| --- | --- |
| 能否在无 Roblox 的环境跑本仓库的测试？ | **能**（已实测：`Logging` 的 8 个真用例全部通过） |
| 能否用 `debug.sethook` 做行覆盖？ | **不能** —— Lune 0.11.1 **没有 `debug.sethook`** |
| 覆盖率怎么办？ | **源码插桩 + `loadstring` + `setfenv`**（已端到端跑通），见 §3 |
| 认证核心的模块还能用 `script.Parent` 吗？ | 能（loader 已解决），但 A 档核心仍**优先构造器注入**，见 §5 |
| 有没用 Roblox 全局？ | 无。`game` 不存在（探针实测 false），所以任何碰 `game` 的模块在 headless 下必然失败 —— 这正是 I16 的可执行形式 |

**最重要的一件副产品**：把测试跑起来当场找到并修掉了 3 个真 bug（§6）。在这之前 8 个用例从未被任何环境执行过。

## 2. 能力矩阵（探针实测）

| 能力 | 结果 | 影响 |
| --- | --- | --- |
| `debug` 表 | 存在 | —— |
| **`debug.sethook`** | **nil（不存在）** | **行钩子路线作废** |
| `debug.info` | 函数 | 可取函数源文件与起始行（覆盖分母用） |
| `debug.getinfo` | nil | 用 `debug.info` 代替 |
| `getfenv` / `setfenv` | 均为函数 | **loader 与插桩的基础** |
| `loadstring` | 函数 | 插桩后的源码靠它加载 |
| `load` | nil | 用 `loadstring` |
| `luau` 库（`luau.load`） | nil | 不能靠它注入环境 |
| `os.time` / `os.date` | 可用 | 时间戳可用；但认证线仍须注入时间（I19） |
| `coroutine` | 可用 | —— |
| `game` 全局 | **不存在** | 碰引擎的模块无法 headless 运行 |

## 3. 结构覆盖的唯一可行路线（决定 C4）

**不可行**：`debug.sethook` + 行钩子（API 不存在）。

**可行并已验证**：把源码文本插桩后 `loadstring`，用 `setfenv` 注入探针收集器。

端到端实测（探针第二轮）：

```
插桩后 f(4) = 210，命中源码行 1,2,3,4,5,6,9,11   → 插桩可加载、可执行、可报告
n=1 时不含"分支行"                                → 插桩能区分取与不取的分支
```

**已知限制（写下来，因为 C4 必须处理）**：

| 限制 | 说明 | 处置 |
| --- | --- | --- |
| 块尾行必须跳过 | 在 `end`/`else`/`elseif`/`until`/`}` 前插语句会破坏语法 | 插桩器要有跳过规则；**真正的实现应基于 Luau 解析器或强约束风格** |
| 多行语句 | 一行一个语句的前提下才安全 | 认证范围已由 stylua 保证一行一语句（但插桩器仍须自测） |
| 分母（可执行行集合） | 需要"哪些行应当被执行" | `debug.info` 取函数范围 + 插桩器自己的统计；**两者不一致即为插桩器 bug** |
| 插桩器自身正确性 | 误插会**高估或低估覆盖** | 见 §7 新风险 R21 |

**因此 C4 的交付物是自研插桩器**，其自身评估按 `CERT.md` §4.4（工具鉴定登记）处理。

## 4. headless 模块加载（决定测试怎么做）

模块里写的是 `require(script.Parent.X)`，Lune 没有 Roblox 实例树。**已验证可行的 loader**：

1. 按**拓扑序**加载（依赖先加载）——这个顺序本来就要算，`Dr.Core.Container.DependencyInjector` 就是干这个的；
2. 每加载一个模块：`loadstring(源码)` → `setfenv(chunk, env)`；
3. `env` 里：
   - `script = { Parent = <已加载的兄弟模块表> }`
   - `require = 恒等函数`（因为 `script.Parent.X` 已经是模块表本身）
   - 显式拷入需要的标准库名字（见 §5 的坑）

实测：`Logging` 的四个模块按 `StructuredLog → LogSink → Logger → Debug` 顺序加载成功，并跑通其 `SelfTest`。

## 5. 两个会咬人的坑

| 坑 | 事实 | 后果 |
| --- | --- | --- |
| **`_G` 不是全局环境表** | 探针实测：`_G.script = …` 赋值后，被 `require` 的模块看不到；`{__index = _G}` 也取不到 `string`/`table` | **必须**显式把需要的全局名字拷进 env（或用 `getfenv()` 取真实全局表），否则模块在 `table.freeze` 这种基础调用上就炸 |
| `warn` 不存在 | Lune 无 `warn` 全局 | 测试失败路径会 `attempt to call a nil value`，掩盖真错误 → loader 必须提供 `warn`（映射到 `print`） |

## 6. 本次探针当场修掉的 3 个真 bug（同一根因）

**根因**：`Logger` 的方法写成**无 self 的闭包**（`info = function(...) `），而调用方用**冒号**（`log:info("a", 1)`）——冒号会把 logger 表本身作为第一个 vararg 传进去。

| 表现 | 影响 |
| --- | --- |
| `log:info("a", 1)` 的消息变成 `table: 0x…\ta\t1` | 每条日志都带一个表地址，且丢语义 |
| `log:SetLevel("debug")` 实际传进一个表 | 报 `invalid level: table`，级别设置完全失效 |
| 3 / 8 个用例失败 | —— |

**修法**：方法改为显式 `self`（`info: (self: Logger, ...any) -> ()`），调用一律冒号；`Debug.luau` 的转发同步改为 `facade:info(...)`。修后 **8/8 通过**。

**为什么之前没被发现**：`SelfTest` 只在 Studio 命令栏手工触发，而**没有人跑过**。这不是"测试写得不够"，是"测试从未执行"。

> 结论（写进门禁 2 的理由）：**未被执行过的测试不是测试，是注释。** headless 通道必须进 CI 且阻断。

## 7. 对计划的改动

| 项 | 改动 |
| --- | --- |
| `STEPS.md` Step 7 的三级探测 | ① `_G` 注入 → **无效**（已实测）② `luau.load(environment)` → **不可用**（`luau` 库不存在）③ 纯逻辑模块 → **有效**，且**扩展到用 loader 加载任意模块**（比原预期更强） |
| `CERT.md` §7.2 的覆盖机制 | 从"`debug.sethook` 行钩子"改为"**源码插桩**"；风险 R18（覆盖工具做不出来）**部分关闭**：路线已通，剩余风险转为 R21 |
| `STEPS.md` Step 7 的"构造器注入"结论 | **软化为偏好而非硬要求**：loader 已解决可测性，`script.Parent` 不再阻碍 headless；但 A 档核心仍优先构造器注入（依赖显式、无加载序耦合） |
| 门禁 2 | 从"应该有"变为"**可行且已证明**"：`lune run` + loader，无需 Roblox |

**新风险 R21**：插桩器自身出错会**污染覆盖结论**（高估→假绿；低估→无谓返工）。对策：插桩器必须有自己的测试，且"插桩器统计的可执行行"与 `debug.info` 的函数范围要交叉校验。
