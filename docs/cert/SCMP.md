## 3. 基线与追溯（7.2.2）

| 时机 | 动作 |
| --- | --- |
| 每个 C-Phase 结束 | 打 tag（`cert-C1`…）、生成 `BASELINE.md`（路径 + sha256 + DAL + 需求 ID 范围） |
| 每次基线 | `TRACE.md` 与覆盖报告**冻结**，与基线同 tag |
| 追溯方向 | 双向：HLR ↔ LLR ↔ 代码 ↔ 测试 ↔ 覆盖（由 `TRACE.md` 生成器执行，禁手改） |

## 4. 变更控制（7.2.4）

认证范围文件（`scope.txt` 列出的）的每次改动必须：

1. 有 **PR 记录**（改了什么、为什么）；
2. 有 **影响分析**：受影响的需求 ID / 用例 ID / 覆盖结论；
3. 走「实现会话 ≠ 评审会话」（§5）；
4. 若改动**扩大或缩小范围** → 更新 `scope.txt` 并核对 `HAZARD.md` §4（范围变更是 CC1 变更）。

**已有的机制**：仓库已装 `main` 提交守卫（禁止直接提交到 `main`，强制功能分支——Step 1 就是被它拦下来的）。它是这套变更控制的原始形态；但它**只拦提交位置，不拦内容**，故 §4 的第 1–3 条仍需人工执行并留证。

## 5. 变更评审（7.2.5）

| 角色 | 职责 |
| --- | --- |
| 实现 | 提交改动 + 影响分析 |
| 评审（**独立会话**） | 核对影响分析、需求映射、覆盖影响；有权拒绝 |
| SQA（`SQAP.md`） | 核对流程是否被遵守；有权阻断合并 |

## 6. 配置状态记帐（7.2.6）

`docs/cert/STATUS.md` 由 CI 生成，内容：

- 每个认证范围文件：是否在基线中、sha256 是否与工作树一致（**漂移检测**）
- 每个需求：代码映射 / 用例 / 覆盖 三项是否齐备
- 未关闭问题报告数（按严重度）
- 门禁 3/10 的最近结果

## 7. 问题报告、跟踪与纠正（7.2.3）

| 字段 | 说明 |
| --- | --- |
| `PR-nnn` | 编号 |
| 来源 | 评审 / 测试 / 覆盖缺口 / 工具发现（`luau-lsp` 属此类） |
| 严重度 | 阻塞（阻止基线）/ 主要 / 次要 |
| 关联 | 需求 ID、代码路径、用例 ID |
| 处置 | 修 / 判为不影响（**须给理由**）/ 降级为已知限制（`shortcut:` + 问题报告号） |
| 关闭证据 | 复现命令 + 结果 |

**规则**：覆盖缺口与"未覆盖行解释"必须能追到一条 `PR-nnn` 或一条书面解释 —— 不允许"看起来没问题"。

## 8. 归档、检索与发布（7.2.7）

| 项 | 做法 |
| --- | --- |
| 归档 | git tag + 发布产物 sha256 记录于 `BASELINE.md` |
| 检索 | 所有认证数据在仓库内 `docs/cert/`，路径即索引 |
| 发布 | 每次发布附 `CERT.md` §10 边界声明；**不得**声称已获适航批准 |
| 保留 | 仓库历史即归档；tag 不可删改 |
