## 1. SQA 的职责边界

SQA 检查的是**过程是否被遵守**，不是"代码写得好不好"（后者是评审的职责）。

| SQA 做 | SQA 不做 |
| --- | --- |
| 核对每条阶段转换准则是否有证据 | 评价算法优劣 |
| 核对需求↔代码↔测试↔覆盖是否四向可追 | 替实现者修 bug |
| 核对变更控制与问题报告是否闭环 | 决定技术方案 |
| 核对认证证据与产品线证据**未混放** | 汇总进度报告 |
| **阻断**：发现过程未被遵守时有权挡住合并 | —— |

## 2. 独立性

SQA 由**独立会话**执行（不参与实现的上下文），并遵守 `SVP.md` §6 的 DV-1 声明：这是**流程独立性**，不是组织独立性，**不声称**后者。

## 4. 阻断权（本项目的实现方式）

| 层级 | 机制 | 现状 |
| --- | --- | --- |
| CI | 门禁 3/5/10 失败即阻断（`set -e` + 显式 exit 1） | ✅ 已实现（门禁 10 含自检） |
| 分支 | 认证范围改动必须走 PR + 评审 | 部分（`main` 提交守卫已存在） |
| 会话 | SQA 检查单 Q1–Q12 未过时**不开基线与 tag** | 本文件即依据 |
| 记录 | 阻断理由写入 `PROBLEMS.md`，不得静默放行 | 待 C6 机制化 |

**一条硬规则**（来自本项目已被验证的教训）：**工具非 0 退出即失败，即使没有输出**。曾因把 `stylua` 的 `exit=2`＋零输出读成"0 个文件需格式化"而差点让门禁假绿（`.plan/STEPS.md` 的方法论陷阱）。SQA 检查 CI 日志时必须核对退出码，不只看输出行。
