# 需求标准（HLR / LLR）

> C2 交付，CC1。约束 `docs/cert/req/` 下的一切需求文本。
> 上游：`PSAC.md`（目标）· `SDP.md` §1（阶段）· `SVP.md` §3（需求驱动测试）。对应 Annex A **A-1/A-2/A-3/A-4** 的表级目标。

---

## 1. 标识体系

| 形式 | 含义 |
| --- | --- |
| `HLR-<MOD>-nnn` | 高层需求：模块**对外可观察**的行为，不含实现 |
| `LLR-<MOD>-nnn` | 低层需求：实现级，必须能一对一映射到代码结构 |
| `TC-<MOD>-nnn` | 验证用例 |
| `PR-nnn` | 问题报告 |
| `<MOD>` | 模块短名，取 `scope.txt` 路径的末段大写（例：`PageManager` → `PAGEMGR`；`BPlusTree` → `BPTREE`） |

**编号只增不复用**。删掉的需求保留原号并标 `WITHDRAWN`（配一条 `PR-nnn` 说明），否则追溯会静默断裂。

## 2. HLR 模板

```markdown
### HLR-PAGEMGR-001

- **需求**：给定一个已存在页的 pageId，`ReadPage` 返回该页当前的槽位内容。
- **激励**：`ReadPage(pageId)` 且该页存在于 `StorePort`。
- **响应**：返回页对象；`pageId`/`slots`/`freeSpace`/`lsn` 与最后一次写入一致。
- **前置条件**：`pageId` 通过 `NamespaceCodec.AssertKey` 校验。
- **后置条件**：不修改存储（读操作无副作用）。
- **危害追溯**：H1（数据永久丢失）
- **验证方法**：测试（`TC-PAGEMGR-001`）+ 评审
- **可判定性**：响应可用字段级相等断言判定
```

**字段全为必填**。缺「危害追溯」的需求不得进入基线（否则 DAL 分配断链）。

## 3. LLR 模板

```markdown
### LLR-PAGEMGR-007

- **需求**：若 `slots` 已满且 `freeSpace < ROW_OVERHEAD`，`InsertSlot` 返回
  `(nil, "PAGE_FULL")`，且**不修改**该页任何字段。
- **实现位置**：`Tri/Storage/PageManager.luau` → `insertSlot`
- **分支/边界**：满页拒写（非覆盖）；`ROW_OVERHEAD` 的定义在 `TYPES.md` §3
- **验证方法**：测试（边界用例 `TC-PAGEMGR-014`）
- **上级需求**：`HLR-PAGEMGR-002`
```

LLR 的要求是**覆盖每个分支、循环与错误路径**——`SVP.md` V-2 的判据就是"LLR 能否逐条落到代码"，所以 LLR 写粗了，V-2 就没法过。

## 4. 可验证性检查单（每条需求必过）

| # | 检查 | 不合格示例（真实反例） |
| --- | --- | --- |
| R1 | **可判定**：有客观判据 | ❌「正确处理边界情况」→ 无法判定 |
| R2 | **无歧义**：单一解释 | ❌「一般情况下返回较快」→ 多解释 |
| R3 | **无实现泄漏**（HLR 层） | ❌ HLR 里写「用开放定址哈希」→ 那是设计，属 LLR/设计描述 |
| R4 | **完整**：含错误路径与边界 | ❌ 只写成功路径 → 错误路径无需求即"意外功能" |
| R5 | **一致**：不与其它需求冲突 | 需与邻近模块需求交叉比对 |
| R6 | **可追溯**：有危害 ID（HLR）与上级 ID（LLR） | 无追溯 = 断链 |
| R7 | **数值有依据**：边界值来自 `TYPES.md` §3 或显式声明 | ❌「最多 64 项」若与页容量推算不符 |
| R8 | **可测**：能用 `SimulatorPort` 上的确定性用例验证（I19） | ❌「在真实 DataStore 上超时时…」→ 那是产品线，不是认证需求 |

## 5. 追溯规则（机检，不靠人眼）

`docs/cert/TRACE.md` 由生成器产出（C3 交付），它同时检查四个方向：

| 方向 | 检查 | 失败含义 |
| --- | --- | --- |
| 需求 → 代码 | 每个 LLR 有实现位置注解 | 需求无人实现 |
| 代码 → 需求 | 认证范围内**无无需求的可执行语句** | **意外功能**（DO-178C 明确要查） |
| 需求 → 测试 | 每条 HLR/LLR 至少一个 `TC` | 孤儿需求 |
| 需求 → 覆盖 | 每条需求所映射的代码行被执行过 | 测了但没跑到 |

**机检靠什么识别**：源码里每个导出函数头上的 `-- LLR-<MOD>-nnn` 注解 + 用例文件头的 `-- covers:` 注解。这是唯一可自动化的锚点，因此：

- 注解缺失 = 追溯缺失 = 门禁 11 失败（不是风格问题）；
- 一个函数覆盖多条 LLR 时写多行注解；
- **不得**把注解当装饰：改代码时要同步改注解，追溯矩阵是生成物，改了注解它就变。

## 6. 评审要求

| 对象 | 评审者 | 检查内容 |
| --- | --- | --- |
| HLR | 独立会话 | §4 的 R1–R8 + 危害映射是否正确 |
| LLR | 独立会话 | 是否覆盖全部分支/错误路径；是否与 HLR 一致 |
| 追溯矩阵 | CI + 人工抽检 | 生成器是否漏识别（注解写错位置） |

## 7. 反模式（本项目已发生过的）

| 反模式 | 后果 | 依据 |
| --- | --- | --- |
| 先写代码再补需求 | 需求会变成代码的"事后描述"，失去发现错误的能力 | `CERT.md` §9.2（已发生：先写了约 5k 行） |
| 需求写成实现清单 | HLR/LLR 分层失效，A-4 的目标失去意义 | §4 R3 |
| 需求写"应尽可能…" | 不可判定 → 无法关闭 | §4 R1 |
| 用人眼维护追溯 | 静默漂移 | §5 |

---

**已实现（C3，2026-10-26）**：`TRACE.md` 由 `scripts/cert-trace-check.luau`（**门禁 11**）生成，四向检查全部机器化（方向 ④ 除外，见下）；位置约定：需求每模块一份 `docs/cert/req/<MOD>.md`（HLR 段 + LLR 段），用例 `tests/cert/cases/<MOD>.luau`，结果 `docs/cert/verify/<MOD>.md`（生成物）。注解锚点就是 §5 说的两个：源码 `-- LLR-<MOD>-nnn`、用例文件头 `-- covers:` + 每条用例的 `covers = {...}`。

**方向 ④（需求 → 覆盖）仍无机器判据**：它需要结构覆盖工具（`CERT.md` 目标 7.2 / **C4**）。因此门禁 11 的绿灯只说明**追溯链完整**，不说明行级覆盖达标 —— 这一点写进了 `TRACE.md` 的末尾，避免被读成"覆盖已达标"。

**自检（证明门禁会失败）**：`lune run scripts/cert-trace-check.luau --selftest` → 正控 1 例 + 负例 7 例，其中 **N1 = 去掉测试覆盖 → `UNTESTED_REQ`（孤儿需求）**、**N2 = 加无注解代码 → `UNSOURCED_CODE`（无需求代码）** 正是 `AC-C3` 要求的两条。真实仓库上也做过同样的负例证明（见 `STEPS.md` 的 Step 72 记录）。

未读/未验证：A-1/A-2/A-3/A-4 的**逐目标编号**（故本文按主题与自定检查单组织，未声称对应某个具体目标号）；`LLR → 代码` 的映射靠**注解声明**而非 AST 解析，注解放错位置是人为错误的残留空间，由 §6 的评审承担。
